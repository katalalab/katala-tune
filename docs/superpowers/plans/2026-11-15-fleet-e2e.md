# Fleet E2E Implementation Plan

**Goal:** tune-coreの収集から保存・再読込・ログ同期までを検証し、全台の欠測を終了コードとJSONに残す。

**Architecture:** tune-cliにe2eモジュールを追加し、既存EngineとStoreだけを使用する。

**Tech Stack:** Rust、Tokio、serde_json、rusqlite（既存）。

**Spec:** `docs/superpowers/specs/2026-11-15-fleet-e2e-design.md`

## 制約とレビュー観点

既存の運用DB・台帳は変更しない。除外機に接続しない。ベンチマーク・ネットワーク設定を尊重する。GUI受入や配布完了をCLI成功から推定しない。全台成功の判定で、対象0台、ログ元の部分失敗、古い保存結果を成功にしない。

## Task 1: CLIの検証契約

- [x] `crates/tune-cli/tests/e2e.rs`に引数拒否・DB保護と収集境界fixtureの統合テストを追加し、未実装で失敗することを確認する。
- [x] `crates/tune-cli/src/e2e.rs`に`pub async fn run(rest: &[String]) -> Result<(), String>`を実装し、mainとdiscoveryに登録する。
- [x] `cargo test -p tune-cli --test e2e --locked`で成功・部分失敗・除外・再読込を検証する。

## Task 2: 全台検証と公開準備

- [x] `docs/development.md`に実行方法とGUI受入との境界を記載する。
- [x] `npm run check`とgitleaksを実行する。履歴OSSチェックは既存mainのコミットメッセージで失敗するため、履歴を書き換えず未解消として記録する。
- [x] 新規private DBで全台E2Eを実行し、成功・未観測・失敗理由をprivate記録に残す。
- [ ] 差分をレビューし、PRを作成する。既存の並行GPUI作業と運用台帳を保全する。

レビューで見つかった異常終了後のJSON受理はJS/Rust収集境界で修正した。失敗時のレポートは本文を含めず分類値だけを返す。IDのraw型、snapshotのplatform marker、保存カーソル値の検証も追加した。実行中の台帳編集を含む整合性は今回の受入対象外で、各実行は台帳を変更せず行った。詳細は`docs/acceptance/fleet-e2e.md`。
