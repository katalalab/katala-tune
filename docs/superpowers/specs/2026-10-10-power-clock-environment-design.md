# 電力・Clockの取得と機体間設定 — 設計案

状態: 2026-10-10 操作者承認済み。実装・配布・実機受入を進める。
基準: main `cabf30f796654006ec1626ee7b2a6ce0ccb95f85`、0.4.2。

## 求める結果

台帳の全Mac / Windows機を、どの機体のKatala Tuneからも選んで、電力、CPU / GPU / VRAMクロック、温度、負荷、電源設定を確認できる。対応する機体には電力上限・クロック範囲・電源モードを、既存の確認と実行記録を通して設定できる。

「相互」は操作卓を固定しないことを指す。設定が互いを上書きし続ける自動同期は設けず、1回の変更には送り元・対象・対象部品・前後値を持たせる。読み取り専用データと変更したい設定値を別に扱う。

個人の機体情報と接続先は既存の私有台帳に置く。公開するソース・合成テストには入れない。SSHの秘密鍵を端末間でコピーしない。

## 現状と方式の比較

既存のWindows分析はGPUのpower.draw / power.limit / 温度を返す。macOS分析は低電力モードと熱制限を返す。ライブのRust `Gpu` は利用率とVRAM量だけを保持する。変更操作にはWindows電源プランがあり、GPU設定・Mac電源モードは無い。

| 方式 | 利点 | 今回の判断 |
| --- | --- | --- |
| 既存の分析・ライブ・SSH・actionsを拡張 | 現在の確認・記録・台帳が使える。どの操作卓からも対象を選べる | 推奨 |
| tune-agent / tune-linkへ調査と変更を全面移行 | SSH不要の経路へ進める | 調査・ライブの経路移行と変更権限設計が未実装。今回の前提にしない |
| 新しい集中管理Webサービス | 1つの画面へ履歴を集約しやすい | 新しい認証・常駐・受け口が必要。既存機能を使う今回の範囲では採用しない |

常時監視は既存のkatala-fleetが担当する。Tuneに新しい24時間サンプラーは足さない。Tuneでは分析時の状態、ライブを見た区間の電力量、入力した稼働時間による試算を扱う。既存の監視履歴を利用できる場合も、元データの期間・粒度・欠測を明示する。

## 取得するデータ

全値に単位、取得時刻、出所、対象部品、実測 / 推定、取得状態を付ける。取得状態は `ok / unsupported / permission_required / unavailable / stale`。取得不可を0へ変換しない。

| 対象 | 数値と設定 | 出所・制約 |
| --- | --- | --- |
| Windows CPU | 名称、基準MHz、性能カウンタからの実効MHz推定、負荷、package W、温度 | CIM / 性能カウンタと、既存センサーの利用可能な数値。CurrentClockSpeedを実効クロックと呼ばない |
| NVIDIA GPU | UUID、GPU / SM / Memory MHz、温度、利用率、VRAM量、P-state、draw W、limit / min / max W、制限理由 | nvidia-smi。ドライバが未対応の列を他の列の取得失敗と分ける |
| macOS | CPU群 / GPUの周波数、SoC / package電力、温度、AC / battery、低電力・対応する電源モード、熱制限 | 既存センサー・OSが取得を許す項目。powermetrics等の管理者権限は自動取得しない |
| 機体全体 | 入力側Wまたは全体W推定、元になった部品と校正設定 | 既存の電力計があれば最優先。部品の電力を機体全体の実測と表示しない |

macOSの手動MHz指定は、OSが対応を確認できるまで操作として提供しない。GPUのメモリ周波数はnvidia-smiのMHzそのものを表示し、実効転送レートへ無条件に換算しない。

## 消費電力量・費用の計算

- ライブ区間: 隣接する有効なサンプルを台形積分する。`kWh = Σ((W前 + W後) / 2 × 秒差) / 3,600,000`。
- サンプルには機体の時刻と単調増加する連番、操作卓での受信時刻を持たせる。再送・逆順・機体再起動・取得元変更を区切り、二重積算しない。
- サンプル間隔の3倍を超える欠測を積分しない。積算できた秒数 / 対象区間秒数をカバー率として返す。機体間の時刻ずれは表示し、受信した順序だけで違う区間を足さない。
- 瞬間値からの試算: `kWh試算 = W × 入力した稼働時間 / 1000`。実測の積算値と別に表示する。24時間稼働を勝手に仮定しない。
- 全体W推定: 非重複のCPU package W・GPU board W・校正したその他Wを合計し、入力側を推定するときだけ電源効率で割る。SoC合計と内訳、電力計の全体値と部品値を重複加算しない。
- その他W・電源効率・稼働時間・通貨 / kWh単価は私有設定。未設定なら必要な計算を「未設定」にする。機種名やTDPだけから実測値を作らない。
- 費用は `対象kWh × 設定した単価` の試算。部分計測の合計には計測できた機体数と欠測機体を添える。

## 機体の設定変更

既存のactions許可リストと、Tauriの確認→台帳再読込→未完了記録→実行→結果記録の経路を拡張する。互換版も同じ検証を行う。

対象はWindows電源プラン、対応するNVIDIA GPUの電力上限・GPU / memoryクロック範囲・既定へ戻す操作、対応するMac電源モード。省電力 / 標準 / 性能プロファイルは機体ごとの設定の集合で、異なるGPUへ同じW / MHzをコピーしない。

1. 対象機体とGPU UUID、対応範囲、現在値、必要な権限、変更対象の古い設定を取得する。
2. 数値の有限性、正値、min <= max、機体が返した範囲を検証する。任意のコマンド文字列は受け取らない。
3. ダイアログに対象・部品・前後値・権限・戻し方を示す。実行直前に機体の同一性・台帳・前値を再確認する。
4. 対象側の短い排他を取得する。違う操作卓から同じ機体 / 部品への変更は待機または競合として返す。変更途中の自動リトライは行わない。
5. 実行後に設定値を読み返す。終了コードだけで成功にしない。GPUの指定クロック範囲と負荷に応じた現在MHzは区別する。
6. 復元可能な前値と実行記録を保存する。操作失敗では変更済みの項目だけを戻し、戻した値も読み返す。

既存のGPU clock lockが読み取れない場合、現在MHzから以前のlockを推測しない。復元できる前stateが無い変更は実行しない。管理者権限やmacOSの組織管理で拒否された項目は理由と必要な操作を示す。

任意の初期W / MHzを全機に適用しない。再起動・BIOS・電圧・ドライバ・新しいstartupはこの構築の既定操作に含めない。再起動後のGPU設定保持が必要な場合は、既存の起動時設定との衝突とバックアップを確認し、具体的な設定値が選ばれた時点で追加する。

## 配布と受入

作業の終点は全対象機への導入と実環境受入。ソース差分・PR・fixture成功だけで完了にしない。

- 対象集合は正典のactiveなMac / Windows物理機から導出する。退役・no-ssh・意図的offlineを分け、各機体の操作卓を検証する。
- 既存のapp / config / DB・稼働中の版を確認し、同じDBを旧版と新版で同時に開かない。ソースhash、配布物SHA256、版を揃える。
- app / configの変更前に復元一式とRESTOREを対象機の私有領域へ保存する。保持は最大30日、成功した導入の古い世代だけを整理し、失敗中の復元材料は保持する。
- 1機体ずつ導入・設定readback・起動・分析・詳細値表示を検証する。既存のstartup設定を保持する。
- 対象集合の自己機体経路と、異なる機体間の全有向経路を記録する。接続成功・調査成功・変更の可否を分ける。
- 対応する設定は、操作者が選んだ1項目で変更→readback→復元→readbackを実証する。未対応機は操作拒否と説明を検証する。

## 検証項目

`npm run check`、公開情報チェックと履歴チェック、JS / Rustの操作一致、Windows PS 5.1のASCII + BOM、両OSの実機GUIを検証する。

計算には既知の一定W / 変動W、欠測、0W、N/A、NaN、重複・逆順・再起動・取得源切替、部品重複、単価未設定を使う。操作には数値範囲、GPU UUID変更、台帳変更、他操作卓との競合、権限拒否、変更後の不一致、復元失敗、キャンセルを使う。未検証のOSや設定は受入表に残す。
