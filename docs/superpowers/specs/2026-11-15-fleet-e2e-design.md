# Rustによる全台E2E検証

全台への更新前後に、GPUIと同じtune-coreを使い、収集・分析・SQLite保存・再読込・ログ同期を一度のコマンドで検証する。GUI表示、配布、アプリ更新の実機受入は別途確認する。

既存の`probe`は結果を保存せず、`logs`は取り込み失敗でも終了コードが成功になる。両者の出力を人が突き合わせる運用では、欠測や保存失敗を全台成功と取り違えやすい。

`tune e2e --db <新規ディレクトリ> [機体ID ...]`を追加する。既存のEngineを直接呼ぶ方式を採る。別のJSランナーは実装と収集経路が異なり、独立したRust収集器は既存の契約を重複させるため採らない。依存追加は不要。

台帳を先に読み、未知の引数・機体ID、不正なIDの重複、空の台帳を接続・DB作成前に拒否する。DBディレクトリは新規作成に限定し、既存の運用DBを開かない。台帳を書き換えず、ベンチマーク・ネットワーク・共用機の設定をそのまま尊重する。除外機には接続しない。

新規Engineで分析結果を保存し、ログを同期してEngineを閉じ、DBを再度開いて今回の成功結果・スコア・ログカーソルが残っていることを検査する。対象ごとに失敗を残し、1台でも失敗した場合と対象0台は非ゼロで終了する。除外数を明示し、除外を成功数に含めない。正常な空ログと、取得失敗・取り込み元の欠測を区別する。

JSONにはスキーマ版、実行時刻、対象・成功・失敗・除外数、機体ごとの各段階の結果を含める。snapshot本体、ログ本文、接続先や鍵は含めない。これは検証用出力であり、一般ユーザーの画面フローは変えない。

検証はCLIを実際に起動し、UnixではSSHの境界だけをfixtureに差し替える。成功、再起動後の保存、部分的なログ失敗、収集失敗、除外、未知ID、既存DB保護、対象0台を確認する。実機結果はprivateな受入記録に保存する。
