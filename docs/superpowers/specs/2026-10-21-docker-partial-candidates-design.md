# Docker Partial候補の別保存・表示

## 目的と採用方針

初回にPartialとなっても、検証・収集終了確認を通ったDockerのpositive factsを内部画面で確認できるようにする。既存のCompleteだけを正式graphへ反映する条件は保持する。未観測networkやedgeを作らず、候補にない対象の削除も推論しない。

比較した案は、診断だけを足すA、inventoryとrelationを分けるB、別candidateを保存するC。Aでは初回の構成が見えず、Bでは不完全なrelationの既知edgeが表示されない。全positive factsを見る目的に合わせCを採用する。

## 確認済みの境界

`db/topology.rs`はPartialをreceiptだけ保存する。`project_rows`は同IDの最初のscope属性を採用するため、候補をaccepted arraysへ単純追加できない。`export.rs`は最新receipt時刻を行へ付けるため、古い正式graphを新しい観測として表示しない修正が必要である。

現行の`collect_docker`と`TopologySnapshot`には取得元・所有プロセス終了確認の証明がない。非空graph、成功exit code、Partialだけをadmissionの代用にしない。収集側の所有者が証拠を発行する境界を接続するまで製品でcandidate保存を有効にしない。

## データと所有権

accepted entities/edges・変更履歴・source cache・cursorは既存のまま保持する。候補は独立tableにscope、attempt_id、source identity/generation、facts時刻、attempt時刻、writer generation、payloadとそのdigestを保存する。内部APIは`candidates`を別配列で返し、`project_rows`へ混ぜない。同IDで属性が違っても両layerは独立する。

candidateは同一の観測内でendpointの両方が確認できたedgeだけを持つ。別engine・別attemptのendpointと結合しない。候補の欠測は正式graphのremove/changeを発生させない。次のCompleteでは従来の正式reconcileを行い、それより古い同scope候補を非表示にする。

候補は最新のadmitted Partialを1件/scope保持する。順序はlive lease generationと収集開始時にDBで予約する単調増加attempt ordinalで決め、壁時計やrun hashで最新を決めない。遅延した古いattemptの保存を拒否し、次Completeの順序も同じledgerで候補に優先させる。後続の失敗attemptでは候補を新規保存・更新せず、旧候補があれば元のfacts時刻と旧attemptで表示し、最新失敗receiptを別に表示する。拒否されたpayloadを候補やcacheへ退避しない。

## Admissionと保存

取得元検証と所有process cleanupの両方が確認されたattemptにだけ、収集境界が非公開constructorからtyped admissionを発行する。attempt・source・facts時刻・payload digestに結び付ける。片方がFailed/Unknown、不整合、timeout、parse、limit、permission、失効writerの場合はcandidate0とする。未解決の関係先によるsemantic Partialは、これらの検査成功と区別する。

保存APIはlive lease holder/generationを同じtransactionで確認し、admissionとpayloadの一致、時刻順序、Partial、Docker scope、重複ID、endpoint closureと上限を確認する。失敗時はcandidateを含むtransaction全体をrollbackする。lease generationはsource generationとは別の概念である。

限界値は1候補8MiB・4096entities・16384edges、全候補64MiB、最大64scope、scope内1候補。候補の期限はfacts観測終了から24時間（86400000ms）で、期限と同時刻から表示しない。保存時にも期限切れを拒否し、読み出し時は期限でfilterし、次回候補書込時に期限切れ候補だけを削除する。量はUTF-8 serialized bytesで測る。上限超過payloadは部分切捨てせず拒否する。global上限は候補だけを古いattempt順でevictし、正式graph/receipt/cache/cursorを削除しない。長さ無制限のID/時刻・NaN類を受け入れない。

## 時刻と表示

facts_observed_at（必要なら開始・終了）とattempt_started/finishedを別に返す。candidateはpayloadに結合した試行区間を使う。accepted graphの実試行時刻は現行snapshot/receiptから特定できないためlast_attempt_at_msはnullとして表示する。receiptの観測時刻はlast_receipt_observed_at_msへ分け、試行時刻と呼ばない。topology_runs.atも実試行時刻の代用にしない。収集時刻はatomic snapshotを保証しない。古い正式graphの行では実際に属性を採用したscopeのComplete反映と同transactionで保存したfacts metadataから元のfacts時刻を保ち、最新Partial/failed receiptの時刻へ付け替えない。metadataのない旧行や不正なmetadataは不明とし、latest/max receiptから推定しない。cache再利用は元のfacts時刻を保つ。

明示的な全件APIはcanonical payload全量の型・再投影・digest検証を維持し、未知versionや破損candidateを返さない。通常UIの部分取得は次の別契約を使う。旧DBへのtable追加は非破壊かつ再実行可能にする。

### 通常UIの部分取得契約（操作者の調整担当が採用済み）

書込時のcanonical全量検証、opaque admission、同transactionのlease確認は維持する。その検証済みpayloadから独立したversion付きenvelopeと正規化したUI行を同transactionで作る。envelopeはscope、attempt、DB ordinal、writer generation、source/settings generation、facts/attempt区間、payload digestを束縛する。各行のdigestは検索列、表示内容、edge端点、envelope識別子を含む。これは通常のprivate DB破損検出であり、悪意あるDB書換えに対する認証や新しい秘密鍵を追加するものではない。

通常UIはcanonical archiveを読まず、同じSQLite read snapshot内のenvelope・ledger・Complete優先・TTL・最新試行情報と、選択した投影行の型/digest/bindingを検証する。検出した投影破損では当該scope全体を非表示にする。未知version、未知schema、投影のない旧形式は候補0とし、raw archiveから自動補完しない。未選択行とarchive全体の潜在破損は未検査である。この限界を返却metadataのvalidation_scopeとarchive未検査状態、画面の部分表示案内で明示し、成功や検証済み0件へ丸めない。

未知のoptional表示table/viewは自動修復せず保持し、正式記録の通常起動とComplete反映を妨げない。表示用indexは既知の実tableについて、生成列・hidden列を含む全列、型、NOT NULL、主キーの列順、一意性、照合順序、既定値と必要な制約を確認して初期化時だけ作成し、read APIでは作成しない。同じ列名と型でも制約が異なる領域は未知として扱う。SQL全文の文字列一致は要求せず、引用・コメント・余白の違う同等の現形式は許す。既定値は実行評価せず、対応するゼロの整数literalだけを認識する。現形式はWITHOUT ROWID（wr=1）・非STRICT（strict=0）に固定する。PK外の新しい一意性を設ける追加unique index・外部キー・CHECK・trigger、未対応の競合処理や照合指定、rowid化やSTRICT化は未知とし、これらを修復・削除しない。SQLiteが同じPK indexへ畳む冗長なUNIQUE宣言は、意味の等しい既知形式として許す。表示領域を利用できなくても既知の有効予約ledgerは更新できるが、ledger自身の形式は独立して確認し、未知なら更新・pruneを省いて正式記録のComplete反映を継続する。Partial候補の保存は未知の表示領域またはledgerでは最初の変更前に拒否し、transactionをrollbackする。型・形式の非互換と真のSQL/IO障害を区別し、後者は呼出し元へ返す。

件数は保存済み投影の総数と条件に合う保存済み投影数であり、全行を再検証した有効件数ではない。backendでfilter/tabと安定順序を適用し、acceptedとcandidateを合計して全体200entities・200edges、edge両端は同じlayer（候補では同scope/attempt）の返却entities内、最大64候補scopeとする。accepted行、receipt、履歴、件数等のmetadataも含む通常UIのserialized応答全体を1MiB以下に制限する。candidateだけを切り詰めてaccepted全量を返す実装ではこの契約を満たさない。文字列・ports等も有界にし、省略と理由、保存総数を返す。byte上限で削減した後もendpoint closureを保つ。全件APIと公開exportは別経路を維持し、公開exportは候補schema・payloadを一切読まないaccepted専用経路を使う。

canonicalの64MiB上限はpayload保存量だけの上限である。UI projection/envelopeは検索列・表示列・digest等の論理データ列を含めて別枠64MiB、最大1,310,720行、最大64候補scopeとする。候補eviction・期限切れ削除では同transactionで対応行を除去する。Completeによる除去は現在leaseに結合した有効予約のordinal以下だけに制限し、遅延した古いCompleteで新しい候補を消さない。未予約・旧holderのreceiptを候補側のCompleteへ昇格させない。この混在writerは製品接続前の未完了ゲートを維持する。索引・WAL等を含む物理DB容量の上限とは称さない。性能比較は全件APIと同じ出力の高速化ではなく、表示目的の部分取得による読取・転送削減として報告する。

内部画面は『最後の正常記録』と『部分観測の候補』を別欄にする。初回は正式graph0でも候補の実体・関係とPartial状態を表示する。前回成功があれば両方を表示し、候補の不足から削除を判断できないことを示す。候補はscope/attempt単位で表示し、最新attempt失敗時は『以前の候補』を明示する。表示件数上限は既存200件を使い、全候補件数と区別する。

候補件数上限の案内では「全件は公開export」を使わず、候補は公開export対象外と明記する。

公開JSON/Mermaidへ候補を追加しない。公開exportは正式graphの匿名kind/label/edge allowlistを維持し、facts時刻と最新attempt時刻の区別のみ安全な数値として反映する。candidate ID、scope、source、generation、digest、attributes、failure本文は公開しない。

## 実装所有と検証

この変更はcandidate model/DB、Docker projection、export、renderer、対応testを所有する。追加合意により`engine_topology.rs`末尾のview/read-only methods、CLI既存topology export armのread呼出し、Tauriのread-only取得/filterも所有する。`collect.rs`、ingestion、予約・保存接続、実witness、remote readerは別担当のまま変更しない。admission発行・保存呼出しはその担当のinterface合意後に接続する。接続前のunit成功を製品完了としない。

必須回帰は初回Partial候補、旧good保持、次Complete、再失敗、unknown admission、payload/source/attempt不一致、lease失効、世代混合、duplicate ID、missing endpoint、容量eviction・entity/edge件数境界・24時間期限境界、facts時刻不変、公開非開示、画面escaping/絞込/件数上限。Rust/JS全体checkと独立レビューを行い、Windows実機の収集・表示受入は別に実証する。

変更のrollbackは候補表示・保存呼出しを無効化する。追加tableは正式graphと独立し、既存データ削除やDB巻戻しを必要としない。正式反映・実機検証が済むまで未完了である。

## 現段階の製品接続ゲート

保存能力型には製品用constructorが無い。cfg(test)だけのsynthetic issuerでDB・表示を検証しており、実データからcandidateを作る製品経路は無効である。診断用ProcessReceiptやexit0をDeserializeして能力へ変換しない。

実装担当間で合意したguardは、一般App内のprocess spawnと独立した収集helper、親側の実helper終了・EOF・承認済みartifact/source確認、全Docker childのbatch証拠、source/settings policyの実入力を要する。これらと実試行時刻のingressが未接続で、local Windowsを含む製品候補保存は未受入である。remote/POSIXは別の所有終了証拠が必要で、remote topologyは無効を維持する。

Cの保存接続には、Complete・失敗・対象外・cache再利用も含む全Docker分岐で収集前予約→同runのreceipt→必要なら候補保存を保証する。能力の発行だけ追加して有効にしない。旧binaryや未予約writerが同じDBへacceptedを適用する場合には、accepted適用revisionを予約・保存・表示へ束縛する対策か、混在を許さない実証済み運用が必要である。現段階ではこの互換・revision保証は未実装で、mixed writer下の時刻bindingやlatest候補を受入済みとは扱わない。

実際の保存接続は専有branchの所有者を明示して順番に行う。DB/UI単体、source review、CIの成功を製品admissionや実機受入の代わりにはしない。
